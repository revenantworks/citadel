# Pack Registry — structural single source of truth *(event-driven surface)*

## Contents

- Build defaults
- The pack registry
- Per pack: members, budgets, seams (foundation · ossuary), capstone, canonical repo

> The canonical roster and pack structure `tools/build.py` derives every
> `references/pack.md` from. **Event-driven** — updated on roster or pack
> changes only, not on a calendar (no staleness stamp). Holds only what a
> *build* needs to name and stamp a member. Brand **styling** — palette, voice,
> taglines, wordmark, firewall — does **not** live here; it lives in
> brandwright's `brand-definition.md` and is applied only when brandwright is
> invoked. The token below is a **label** (it names skills and stamps
> frontmatter); it applies no styling on its own.

**foundation budgets** *(body-footprint table — one row per member; `build.py` validates each member's measured SKILL.md body against its row)*

Declared here rather than in each member's frontmatter, changed 2026-07-27. The gate is unchanged — a body's size must be **declared and justified**, per the item-③ rescope — but the justification is build-time data, and frontmatter is loaded on every single invocation of the skill. A `why` in `metadata.body_budget` cost 51–95 tokens per member *every time that member ran*, to explain a number no runtime reader ever acts on. That is the exact waste tokenwright exists to find, sitting in the pack's own gate. The registry is already `build.py`'s single source of truth, no member loads another member's registry, and nothing here ships in a member's zip — so a row costs zero runtime tokens. **That is what makes declaring all eight affordable**: eight frontmatter blocks would have cost ~400 tokens per session to say that five members have no size problem.

**Standalone skills built outside a pack keep `metadata.body_budget` in frontmatter** — they have no registry to declare into, so the frontmatter form stays valid and `build-templates.md` still teaches it. It is the pack-member case that moves.

That was true when the row was authored but stopped being true at skillwright 1.2.0, when finding 16 of that release added skillwright's own boundary clause — "for authoring or scoring an eval suite as its own job, evalwright" — to close its two nearest-neighbour gaps. The lesson generalizes: a seam row is a claim about two files, and it goes stale the moment either file changes without a registry pass in the same commit — the same class of gap the skillwright ↔ agentwright note below exists to name.

- **dispatchwright ↔ {promptwright, rigwright, agentwright}** (added 2026-08-18): `build.py --check` flagged dispatchwright as "named in no routing seam" from its 1.0.0 release (2026-08-18) forward. The three edges are real and were never in doubt — dispatchwright's own SKILL.md §1 states them by quoting the sibling that owns the other half of each ("The tier table is promptwright's," "Where the trigger lives is rigwright's," "Unattended runs are agentwright's, whole") — but the rows were never added to this table, and the member's own README named the gap explicitly under "What did not land at 1.0.0" rather than leaving it silent. All three rows are now present above. Every edge is genuinely uncontested rather than negotiated: none of promptwright's, rigwright's, or agentwright's descriptions mention dispatchwright or fan-out dispatch by name, so nothing on their side claims the territory dispatchwright is ceding or taking — the split is dispatchwright unilaterally staying out of model-picking, hook-placement, and unattended scheduling, not a boundary either sibling had to give ground on. The signal column reads **one description** on all three for that reason, not as a mark against them: an uncontested edge stated on only one side is not the same failure mode as the evalwright ↔ skillwright row above, where the claim was actively wrong. The warning `--check` prints is therefore now informative rather than a real gap — it should be read as "three declared, uncontested edges," and should stop firing once the three rows above are live in a build.

- **skillwright ↔ agentwright** (added 2026-07-27, pack 1.3.0): closed a boundary that shipped one pass earlier claimed from one side only. agentwright 1.2.0 and skillwright 1.4.0 each took a security capability and each wrote a reciprocal boundary sentence into its own `description`, but the row itself was deliberately skipped that pass because adding it regenerates all eight manifests — so the seam existed in routing metadata and nowhere the table could see it. Both sides carry the claim, so the signal reads **both descriptions**; the cold re-run that would instrument it is owed and disclosed, not claimed.
