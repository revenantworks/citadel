### Doctrine findings

Four patterns, two of which are shared root causes across multiple cases.

**1. ROOT CAUSE OF THE CASE 11 FAIL — a P0 rule that depends on a number the Load budget does not load, and the number the model supplies is wrong.** SKILL.md's Audit entry defines P0 as "a description past its platform cap" and never names the cap. Grep across the entire declared load path (SKILL.md + measurement.md + waste-taxonomy.md) returns no description character cap at all. Worse, the one `1,024` that IS in the load path is OpenAI's cache-prefix threshold *in tokens* (measurement.md line 44) — a units false-friend sitting right where a model reaching for "the cap" will find it. Live verification against primary docs: the real cap is **1,536 characters** (combined `description` + `when_to_use`, configurable via `skillListingMaxDescChars`); no 1,024-character cap is documented. So tokenwright's flagship P0 is unenforceable from its own load path, the fallback is model memory that is wrong by 512 characters, and its honesty rules cannot catch the error because there is no stamped source to check against. This is not confined to the cap: the Cache rule tells users a reorder is cache-positive without measurement.md carrying Anthropic's minimum cacheable prompt length (512–4,096 tokens, model-dependent), below which `cache_control` is silently ignored with no error — so tokenwright can currently recommend a reorder for a prefix that cannot cache at all. measurement.md is the file whose entire job is platform reference points; the three numbers most load-bearing for its own P0 and Cache rule are the three it lacks. Fix: those numbers belong in Platform reference points, stamped, and the Audit entry should cite them rather than saying "its platform cap".

**2. `estimate (±15%)` launders an unmeasured input as arithmetic — and no case in the suite can catch it.** Three independent instances in this run. (a) Case 2: I emitted 811→349 with the `estimate (±15%)` label and the `chars ÷ 4` arithmetic shown; measured 977→410 — the before-count 17% low, i.e. outside the very band it wore. (b) Case 14: same failure, claimed 470→371, measured 401→358. (c) Different mechanism, same doctrine hole: my counting tool (PowerShell 5.1, ANSI default) returned **bytes, not characters**, for every UTF-8 file, silently inflating counts on ordinary English text containing em dashes, ×, ÷, ≤. Method-ladder rung 2 specifies the ratio and the band but never says how to obtain the character count, and never says a tool is required — whereas rung 1 carefully names the tokenizer. measurement.md warns "Non-Latin scripts: measure, don't assume" but not that Latin text with typographic punctuation breaks a naive count. The ±15% band absorbs all three failure modes and renders them invisible. The compounding problem is test-coverage: **no case in the suite asserts count accuracy**. Case 1 asserts "after-count ≤ 2,000 **by the stated method**" — self-certifying. That is why an 18-case suite could pass 17 while three real measurement defects went through it.
